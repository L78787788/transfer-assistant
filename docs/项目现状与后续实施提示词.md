## 3. 已完成的总体架构

```text
Flutter UI
  ├─ 附近设备
  ├─ 传输任务
  └─ 设置
       │ JSON 命令 / JSON 事件，不传文件内容
       ▼
最小 Dart FFI
       │
       ▼
Rust TransferCore
  ├─ Tokio 网络运行时
  ├─ mDNS 发现
  ├─ rustls TLS 1.3
  ├─ Protobuf 控制协议
  ├─ 多通道块传输
  ├─ BLAKE3 完整性校验
  ├─ SQLite 状态与断点位图
  └─ 文件系统与路径安全
       │
       ├─ Windows C++：文件选择、目录、托盘、DPAPI
       └─ Android Kotlin/JNI：SAF、FD、Keystore、前台服务和系统锁
```

该架构满足最关键的性能约束：文件字节不会经过 Dart，也不会因为 Flutter 状态管理产生大块内存复制。

## 4. 已完成的 Rust 传输内核

### 4.1 网络和发现

- 使用 Tokio 多线程运行时处理监听、控制连接和数据连接。
- 默认监听 TCP `53317`；端口占用时自动选择空闲端口。
- 使用 `_transassist._tcp.local.` mDNS 服务发现局域网设备。
- 发现失败时可以通过 `IP:端口` 手动添加设备。
- 使用 TCP `NODELAY` 降低控制和小块消息延迟。
- 每个任务最多四条并行数据通道。
- 全局最多两个活动传输任务。

### 4.2 加密和身份

- 首次运行生成持久 Ed25519 设备身份和 TLS 证书。
- 使用 rustls 实现 TLS 1.3 双向证书认证。
- 从实际 TLS 握手证书计算并验证证书指纹。
- 首次连接根据握手双方信息生成对称六位验证码。
- 双方确认后固定设备 ID 与证书指纹。
- 指纹改变时不会继续沿用旧信任关系。
- Windows 使用 DPAPI 保护身份数据。
- Android 使用 Keystore 包装 AES 密钥，Rust 以 AES-GCM 加密身份文件。

### 4.3 控制协议

- 使用 `prost` 生成 Protobuf 类型。
- 控制帧采用四字节大端长度前缀。
- 单控制帧上限为 1 MiB，在分配缓冲区前检查长度。
- 协议包含 Hello、连接类型、传输报价、清单分页、配对确认、接收决定、断点位图、任务控制和结果消息。
- 已增加 v1 Hello 黄金字节测试，用于防止字段编号被意外改变，但该新增测试尚未在当前源码上跑通。
- 已添加 `cargo-fuzz` 控制消息解析入口，尚未实际完成编译验证。

### 4.4 文件块与性能策略

- 默认块大小为 4 MiB。
- 每块包含任务 ID、文件 ID、块序号、文件偏移、长度和 BLAKE3 哈希。
- 接收端先验证块计划、边界和哈希，再写入临时文件。
- 支持定位读写和顺序读写。
- 不可随机访问的文件描述符自动降级为单数据通道。
- 四通道乘 4 MiB 块及传输流水线按 64 MiB 设计上限约束。
- 数据块不会通过 Dart FFI。
- 任务进度包含已完成字节和近似每秒速度。

### 4.5 文件夹和路径安全

- 支持单文件、多文件、文件夹和混合批量清单。
- 清单按页发送，每页默认 1000 个条目。
- 保留目录结构和空目录。
- 拒绝空路径、绝对路径、Windows 盘符、反斜杠、`.`、`..`、空片段、NUL 和过长路径。
- 扫描时跳过符号链接和 Windows 重解析点。
- Windows 非法字符会进行确定性转换。
- `CON`、`PRN`、`AUX`、`NUL`、`COM1`、`LPT1` 等保留名称会安全转换。
- 接收端重名使用 `名称 (1)`、`名称 (2)`，不会静默覆盖。
- 所有块完成并同步后才把 `.part` 原子改名为最终文件。

### 4.6 持久化和断点

- 使用 rusqlite 和内置 SQLite。
- 保存可信设备、任务、文件清单、源版本、临时位置、最终位置、完成块和设置。
- 已实现 schema v1 到 v2 的迁移，v2 增加传输速度字段。
- 应用重启时，未完成任务恢复为“中断”。
- 接收端根据 `.part` 文件和完成块表生成断点位图。
- 发送端只调度接收端缺失的块。
- 已完成 Windows 发送端重启后重建任务清单并使用原任务 ID 重试的测试。
- 当前正在把同样能力扩展到 Android SAF 持久 URI。

- 最低 Android 9，`minSdk = 28`。

### 阶段 1：完成 Android 持久 URI 恢复

目标：Android 发送任务在应用进程退出后仍能用同一任务 ID 重试。

技术：

- Android `ContentResolver`。
- `ParcelFileDescriptor` 所有权转移。
- Kotlin/JNI 静态桥。
- Rust `File::from_raw_fd`。
- SAF persistable URI permission。
- SQLite 持久源引用。

方法：

1. Kotlin 根据 URI 重新打开只读 PFD。
2. `detachFd()` 后返回 FD 和随机访问能力。
3. Rust 把 FD 包装为唯一拥有者 `File`。
4. 使用同一 URI 查询 size 和 last-modified，形成稳定源版本。
5. 每块读取前比较源版本。
6. 权限失效转为可重试错误，提示用户重新选择来源。
7. 保留 transfer ID 和 item ID，使接收位图可以继续匹配。

验收：Android arm64 Rust Release 和签名 APK 构建通过；真机杀进程后重试只补缺失块。

### 阶段 2：补齐传输状态和清理语义

目标：暂停、取消、失败、重试、断开和重启在两端状态一致。

方法：

- 逐条审计状态机允许的转换。
- 对控制连接和四个数据连接使用统一取消信号。
- 接收端取消时先阻止新写入，再关闭 FD，最后删除临时文件。
- 重试时以接收位图重置发送端完成字节，防止累计超出总大小。
- 接收控制连接异常时保留临时数据并进入 Interrupted。

验收：没有死锁、任务不会永久停在 Preparing/Verifying、取消后无 `.part` 数据。

## 12. 最终预期效果

完成后，用户在任意两台受支持设备上打开传输助手，即可在附近设备页看到同一局域网内的设备。首次连接时双方核对相同的六位验证码；选择文件或整个文件夹后，数据通过 TLS 1.3 直连传输。任务页实时显示进度和速度，用户可以暂停、继续或取消。

网络中断、Wi-Fi 切换或应用重启不会要求从头传输；双方重新连接后只发送接收端缺失的 4 MiB 块。接收内容在全部 BLAKE3 校验通过前保持为临时文件，完成后才出现最终文件。重名内容自动编号，不覆盖用户已有数据。

Android 在后台传输时显示前台通知并持有必要系统锁；Windows 可以驻留托盘。最终交付固定密钥签名的 Android arm64 APK、Windows Inno Setup EXE、SHA-256 校验文件、自动化测试和 CI。
